# Performance measurements and optimization report

## Scope

These are **executed synthetic, single-process measurements**, not a concurrent-user capacity test, API/network SLA, managed-database benchmark or low-end Android certification. The measurements never open a school database and must not be used as production dashboard statistics.

Reproduce from the repository root with the development lock installed:

```sh
.venv/bin/python scripts/benchmark.py \
  --records 1000 5000 --questions 20 --iterations 3 \
  --output .cache/qa/performance.json
```

The script is bounded (at most 10,000 synthetic responses, 500 questions, 20 samples), checks actual rank/percentile outputs and actual native CV answers, and writes only aggregate timings/checksums/version information. Fixture generation is outside each timed call. Each analytics sample includes real validation, deterministic scoring, fingerprinting, ranking and question statistics; each optical sample includes decoding, registration, image processing, pixel measurement, coordinate/preview output and barcode decoding, with OCR explicitly disabled.

## Environment and method

- Local Linux x86-64 sandbox, **2 logical CPUs**.
- CPython **3.11.2**, OpenCV **5.1.0** with **2 threads**, NumPy **2.4.6**, SQLAlchemy **2.1.9**.
- `perf_counter` wall time; three consecutive calls per case, including the first call rather than hiding it as warm-up.
- p95 is **nearest-rank** over these three samples (therefore the largest sample), not a statistically stable tail-latency estimate.
- No concurrency, external services, physical camera or artificial network delay in this benchmark. Shared-host scheduling and caches affect results.

## Ranking optimization — same outputs, less work

The backend previously scanned all evaluated percentages for every student: **O(n²)** percentile calculation after scoring. It now sorts percentages once and uses binary search: **O(n log n)** indexing/lookup. Competition ranking remains `1, 1, 3`; percentile remains `100 × strictly lower evaluated percentages / evaluated count`. It does not substitute score rank for percentage rank; sets with different keyed maxima can legitimately have different score and percentage orderings.

Every seventeenth synthetic response is review-only and excluded from the denominator. Test keys/results are deterministic; no production statistics or simulated optical detections are generated by this fixture.

| Input responses × questions | Evaluated | Before median | After median | Observed median reduction | After nearest-rank p95 |
| --------------------------- | --------: | ------------: | -----------: | ------------------------: | ---------------------: |
| 1,000 × 20                  |       941 |    264.866 ms |   235.533 ms |                     11.1% |             240.486 ms |
| 5,000 × 20                  |     4,705 |  2,409.447 ms | 1,240.125 ms |                     48.5% |           1,349.805 ms |

Checksums of `[result ID, score, competition rank, percentile]` were **identical before and after**, and a new regression checks ties, review exclusion and differently keyed set maxima. This is an observed local change, not a promise that all endpoints or devices are 48.5% faster. The browser's ranking code already uses a sorted percentage index; no intentional API/formula change was made.

## Native OpenCV measured workload

These after-fix fixtures pass through the genuine engine; no answer key influences image detection. The known selections are checked **after** measurement.

| Fixture                                         | Answers measured |     Median | Nearest-rank p95 | Flagged in these samples |
| ----------------------------------------------- | ---------------: | ---------: | ---------------: | -----------------------: |
| Clean sheet                                     |               20 | 354.730 ms |       373.009 ms |                        0 |
| Dark exposure                                   |               20 | 323.217 ms |       330.508 ms |                        0 |
| Uneven horizontal shadow                        |               20 | 307.462 ms |       318.099 ms |                        0 |
| Last page of 500-question, five-page A–E layout |              100 | 318.883 ms |       322.777 ms |                        0 |

Peak **cumulative process RSS** for the entire ranking/CV benchmark was **276,444 KiB (about 270 MiB)**. This includes Python/imports, generated fixtures, prior cases, arrays, previews and allocator retention. It is **not** per-sheet memory, browser WASM memory or a safe container-memory limit.

The larger correctness corpus separately exercises dark/bright/faded/shadowed images, rotations/perspective, all option counts, circle/square radii 5–25, JPEG/half-resolution input, blur, blank/partial/residue/multiple/crossed marks, wrong templates, key independence and a 500-question final page. Severe blur is rejected; moderate blur requires review. Those are synthetic safety checks, not a physical accuracy percentage.

## Application/build observations

- Production TypeScript/Vite/PWA build passed. At this checkpoint, **51 precache entries / 23,118.81 KiB (about 22.6 MiB)** retain offline CV, OCR and PDF operation.
- Lazy chunks remain large: ExcelJS about **940 kB raw / 271 kB gzip**, PDF about **501 kB / 150 kB**, charts about **465 kB / 129 kB**. The build warning is retained, not hidden by raising its threshold.
- The expanded genuine browser workflow passed in approximately **48 seconds test time** against a fresh local PostgreSQL schema. It includes first-run setup, imports/accounts, server scanning, corrections, exports, four browser exposure scans, unsafe-grid rejection, privacy, offline reload/PDF/sync and 36 responsive checks. This duration is **test execution time, not page-load latency**.
- Durable workers now release their database connection/transaction while CV/OCR runs, use attempt-fenced commits, and recheck current authorization. This avoids occupying a pooled connection throughout a long image read; no throughput number is inferred from the implementation.
- PostgreSQL/SQLite parity tests exercise constraints, rollbacks and worker concurrency. Paginated student/audit/batch APIs have bounds; the current rich/offline workspace still materializes a broad authorized projection. No large-school query/load benchmark is claimed from unit tests alone.

## Remaining performance acceptance

1. Real network/HTTPS API p50/p95/p99, concurrent teachers/scanners, PostgreSQL query plans/index selection and connection-pool saturation on the intended deployment.
2. Representative 500-question cohorts, many subjects/schools/history/originals, cold caches, report-generation memory, hundreds of uploads, background-worker restart/backpressure and external S3 latency/failure behavior.
3. Physical low/mid-range Android devices: cold start, WASM initialization/heap, PDF rasterization and multi-image queue memory, camera frames, battery/thermal throttling, storage pressure and offline service-worker install/update/eviction.
4. Further reducing the static precache without breaking explicitly required offline OCR/PDF/scanning. Do not remove large assets and call the app optimized while offline acceptance fails.
5. Production resource limits, image/container sizing, worker count and operator capacity/alert thresholds selected from measured workloads, not guessed from these fixtures.

Raw local evidence: ignored `.cache/qa/accuracy/performance-{before,after}.json`, build and browser logs. Source and correctness checks are committed; private/generated datasets are not.
