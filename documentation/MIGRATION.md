# Preserving the existing Node workspace

1. Keep the existing `markly.sqlite`, its backups, and the baseline commit `8b5360f`. Stop writes to the old service during the final cutover. Do not point SQLAlchemy at the Node database file: the schemas are different.
2. Install Python 3.11+ and run `python -m venv .venv`; install `backend/requirements.lock`. For PostgreSQL set `DATABASE_URL` to a new, empty database and configure `DATA_DIR`, `BACKUP_KEY`, and other secrets as documented in the deployment guide. With no URL the destination is `.data/enterprise.sqlite`.
3. Review the source path, then run `.venv/bin/python -m backend.cli migrate-node .data/markly.sqlite --confirm`. This uses SQLite's consistent backup API (including WAL state), opens the original read-only, validates the documents, and imports all records in one destination transaction. It refuses to import into a nonempty destination. It retains a private, consistent copy of the source before migration. No source data or historical backup file is deleted.
4. Sessions are deliberately not imported; sign in again. Legacy salted scrypt hashes are verified for migration compatibility, then upgraded to Argon2id after a successful sign-in. No passwords are exposed. Legacy teacher accounts have **no class assignments until a school admin grants them**; there is no implicit all-school teacher access.
5. Verify institution/student/exam/result counts, corrected scores, layouts/logos, originals, permissions and representative reports before retiring the Node service. Existing Node recovery files remain available to the baseline; enterprise recovery points are encrypted separately.
6. If validation fails, no destination school data is committed. Fix/export the source document deliberately, or continue running the preserved baseline. Do not reset the source to work around validation errors.

For trusted-server recovery use `.venv/bin/python -m backend.cli reset-password account@school.edu`. Password and confirmation are read with hidden terminal prompts, never CLI arguments, and all old sessions are revoked. A school admin can reset a single-school member after verifying their own password; they cannot reset a multi-school account or super administrator.
