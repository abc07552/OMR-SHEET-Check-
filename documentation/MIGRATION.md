# Preserving the existing Node workspace

1. Keep the existing `markly.sqlite`, its backups, and the baseline commit `8b5360f`. Stop writes to the old service during the final cutover. Do not point SQLAlchemy at the Node database file: the schemas are different.
2. Install Python 3.11+ and run `python -m venv .venv`; install `backend/requirements.lock`. For PostgreSQL set `DATABASE_URL` to a new, empty database and configure `DATA_DIR`, `BACKUP_KEY`, and other secrets as documented in the deployment guide. With no URL the destination is `.data/enterprise.sqlite`.
3. Review the source path, then run `.venv/bin/python -m backend.cli migrate-node .data/markly.sqlite --confirm`. This uses SQLite's consistent backup API (including committed WAL state), opens the original read-only and imports **from the retained snapshot**, so record reads and the safety copy describe the same state. It validates the documents and imports records/preferences in one destination transaction. It refuses a nonempty destination and source/destination equality. The private source snapshot has mode `0600`. No source data or historical backup file is deleted; the CLI returns actual user/school/student/examination/result counts for reconciliation.
4. Sessions are deliberately not imported; sign in again. Legacy salted scrypt hashes are verified for migration compatibility, then upgraded to Argon2id after a successful sign-in. No passwords are exposed. Legacy teacher accounts have **no class assignments until a school admin grants them**; there is no implicit all-school teacher access.
5. Verify institution/student/exam/result counts, corrected scores, layouts/logos, originals, permissions and representative reports before retiring the Node service. Existing Node recovery files remain available to the baseline; enterprise recovery points are encrypted separately.
6. If validation fails, no destination school data is committed. Fix/export the source document deliberately, or continue running the preserved baseline. Do not reset the source to work around validation errors.

For trusted-server recovery use `.venv/bin/python -m backend.cli reset-password account@school.edu`. Password and confirmation are read with hidden terminal prompts, never CLI arguments, and all old sessions and pending reset tokens are revoked. A school admin can reset a single-school member after verifying their own password; they cannot reset a multi-school account or super administrator.

Automated SQLite/PostgreSQL drills in `backend/tests/test_maintenance.py` cover two schools, duplicate IDs scoped across schools, 500-question A–E/five-page records/templates, scoring/reports/preferences, unchanged source/WAL fingerprints, legacy password upgrades, no imported sessions, unassigned teachers, populated-destination refusal and all-record rollback when the second school is invalid. Recovery tests verify hidden-prompt handling, confirmation mismatch, session/token revocation and record preservation. See [TESTING.md](TESTING.md). Rehearse with a representative private backup before a real cutover; synthetic fixtures do not establish compatibility with every historical/custom database.

If using the enterprise container, run the maintenance command in an explicitly authorized one-off container with the same destination secrets and a **read-only source mount**, not by pointing `DATABASE_URL` to the Node file. Keep writes quiesced until count/score/layout/evidence reconciliation and rollback review are complete. Production deployment, key preservation and disaster-recovery requirements are in [DEPLOYMENT.md](DEPLOYMENT.md).
